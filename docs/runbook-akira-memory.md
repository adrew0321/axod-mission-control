# AKIRA memory vault — setup

AKIRA's long-term memory is a private git repo checked out on the Mini at
`data/akira-memory/`, synced to your laptop Obsidian.

## One-time

1. **Create a private GitHub repo** `akira-memory`. Leave it empty —
   `pnpm vault:migrate` (Step 4 below) seeds the zone structure, the root
   `CLAUDE.md`, and the root `INDEX.md` on its first run.
2. **Mini deploy key:** as `mc`,
   `ssh-keygen -t ed25519 -f ~/.ssh/akira-memory -N ""`; add the `.pub` to the repo's
   Deploy keys with **write** access; add a host alias in `~/.ssh/config`
   (`Host github-akira-memory` / `IdentityFile ~/.ssh/akira-memory`).
3. **Clone on the Mini:**
   `sudo -u mc git clone git@github-akira-memory:<you>/akira-memory.git /srv/mission-control/data/akira-memory`
4. **Set the PIN + (optional) paths** in the Mini `.env`:
   `AKIRA_MEMORY_PIN=<your unlock PIN>` (optional `AKIRA_MEMORY_DIR`, `AKIRA_MEMORY_PULL_MS`).
   Restart `mission-control`, then run `cd /srv/mission-control && sudo -n -u mc pnpm vault:migrate`
   (see "Restart-then-migrate ordering" below for why that order matters).
5. **Laptop:** clone the repo, open the folder in Obsidian, enable the **Git plugin**
   (auto pull/commit/push on an interval).

## Zone structure

The vault root holds `SOUL.md`, `SOUL.proposed.md`, a `CLAUDE.md` (the vault's
own navigation map, injected into AKIRA's turn as `## VAULT`, editable in
Obsidian), and a root `INDEX.md` (the zone map — see "What `INDEX.md` means"
below). Seven zones live under it:

```
data/akira-memory/
  CLAUDE.md                 # conventions + navigation pattern (injected)
  INDEX.md                  # top-level zone map (seeded, then AKIRA-maintained)
  SOUL.md
  SOUL.proposed.md
  memory/                   # AKIRA-owned. remember/forget only. Do not hand-edit.
    INDEX.md                #   recall index (code-generated)
    <slug>.md
  projects/<project-id>/    # per-project knowledge, keyed by projects.id
  ops/                      # runbooks, machine topology, backup chain, incidents
  research/                 # raw captures distilled into durable pages
  outputs/                  # specs, plans, reports worth finding again
  personal/                 # goals, journals, reviews
  skills/                   # named workflows; one folder per skill, each a SKILL.md
    <name>/SKILL.md
  .claude/
    skills -> ../skills     # symlink; how the SDK discovers the skills above
```

The `.claude/skills` symlink is what lets skills live somewhere Obsidian can
edit. `pnpm vault:migrate` creates it. Its `Skills:` output line is the only
place the symlink is ever proven — Windows cannot create it, so it reports
`unsupported` on the dev laptop and must report `created` or `exists` on the
Mini. `occupied` means something that is NOT a symlink is sitting on the path;
remove it and re-run, or AKIRA sees no skills at all.

AKIRA's enabled skill list is read from `skills/` on every turn (not `'all'` —
that would also pull in Mission Control's own `.claude/skills`, since her cwd is
the repo). A skill she writes with `vault_write` is live on her next turn.

Every zone folder gets a stub `INDEX.md` on migration; AKIRA maintains it
after that (add a line for every document you add to a folder, same turn).
Only `memory/INDEX.md` is regenerated by code — never hand-edit it.

### What `INDEX.md` means, and where

- `memory/INDEX.md` — the generated recall index (code-generated, one line per
  note, newest first). This is what a flat pre-migration vault's root
  `INDEX.md` used to be.
- Every other `INDEX.md` (root and each zone folder) — a human-and-AKIRA
  maintained map of what's in that folder. The root one is the zone map, not a
  recall index.

## Migrating an existing flat vault to the zone layout

Run `pnpm vault:migrate` (locally: `pnpm vault:migrate`; on the Mini:
`sudo -n -u mc pnpm vault:migrate` from `/srv/mission-control`). It:

- creates `memory/`, the five domain zones, and `skills/`,
- moves every existing flat note into `memory/`, leaving `SOUL.md` and
  `SOUL.proposed.md` at the root,
- seeds the root `CLAUDE.md` and a fresh root `INDEX.md` zone map, plus a stub
  `INDEX.md` per zone (only when each is missing — never on a re-run),
- regenerates `memory/INDEX.md`,
- creates the `.claude/skills` symlink and copies the shipped skills from the
  repo's `vault-seed/skills/` — only when a skill of that name is absent, so an
  edit made in Obsidian always wins,
- commits the result in the vault's own git repo (does **not** push — push
  stays a manual, deliberate step).

It is idempotent: safe to run more than once. A second run moves nothing and
never touches a root `CLAUDE.md`, root `INDEX.md`, or zone `INDEX.md` that
already exists — those are yours once written.

If any note cannot be moved (a filename collision with a note already in
`memory/`), the script prints it under `STRANDED at the vault root` and exits
non-zero. A stranded note is invisible to AKIRA (she only ever reads
`memory/`) until you resolve it by hand — rename or merge it into `memory/` —
and re-run.

### Restart-then-migrate ordering

`memoryDir()` falls back to the vault root when `memory/` doesn't exist, which
makes **deploy-before-migrate** safe: a pre-migration vault keeps reading and
writing exactly where it always did, whether the new code has landed or not.

**Migrate-before-restart is not safe.** If you run the migration while the
*old* build is still serving, that old build is still calling `vaultDir()` for
notes. Once the migration empties the root, its `## MEMORY` and `## LESSONS`
blocks go silently empty, and any `remember` call in that window writes a note
to the root that the new build (which only reads `memory/`) will never see.

**Always restart the new build first, then migrate.**

### Caveat: deleting `memory/` while a hand-edited root `INDEX.md` survives

`migrateVault`'s only signal for "has this vault already been migrated" is
whether `memory/` exists. If an operator deletes the whole `memory/`
directory but the root `CLAUDE.md` and `INDEX.md` survive (including any
hand-edits made in Obsidian), the next migration run reads `alreadyMigrated`
as `false` and treats it as a first run — the root `CLAUDE.md` is left alone
(it's only ever written when missing), but the root `INDEX.md` **is**
overwritten with a fresh zone map, discarding those edits.

This is recoverable: the vault is a git repo, so `git log` / `git checkout`
against the vault's own history recovers the pre-overwrite `INDEX.md`. It is
not, however, silent-safe — don't delete `memory/` casually.

## Notes
- The app repo ignores `data/akira-memory/` — it's a separate repo.
- Memory is plaintext (so Obsidian can read it); privacy = private repo + login + the
  PIN-locked Settings panel. Never store secrets in memory.

## Updating a shipped skill in the live vault (one-time operator step)

`pnpm vault:migrate` copies skills from `vault-seed/skills/` **only when a skill
of that name is absent**. That is deliberate — an edit made in Obsidian must
always win over a shipped copy. The consequence is that changing a skill in this
repo does **not** update the copy already in her vault.

So when a shipped skill is revised (as `vault-gardening` and `distil-research`
were in v1.26.0, to use `list`/`read`/`bash` on `target: "host"` instead of the
`Read`/`Glob`/`Grep` tools she never had), the live copy must be replaced by hand:

1. **Check she has not edited it first.** In the vault:
   ```bash
   cd /srv/mission-control/data/akira-memory
   git log --oneline -- skills/<name>/
   ```
   If the only commits are migrations, overwriting is safe. **If she or the
   operator has edited it, stop** — reconcile by hand rather than clobbering; the
   only-when-absent rule exists precisely to protect that edit.

2. Copy the revised skill in and commit it in the vault's own repo:
   ```bash
   sudo -u mc cp /srv/mission-control/vault-seed/skills/<name>/SKILL.md \
     /srv/mission-control/data/akira-memory/skills/<name>/SKILL.md
   cd /srv/mission-control/data/akira-memory
   sudo -u mc git add skills/<name>/SKILL.md
   sudo -u mc git -c user.name=AKIRA -c user.email=akira@axod \
     commit -m "skills: update <name> from vault-seed"
   sudo -u mc git push
   ```
   **Do not skip the push.** Every write AKIRA makes through `vault_write` goes
   through `gitCommitPush`, which commits *and* pushes. A hand-made commit that
   is only committed lands on the Mini's disk alone — the private
   `adrew0321/akira-memory` remote and any Obsidian mirror never see it, and the
   next `gitPullDebounced` can stall on the divergence.

3. No restart or reseed is needed — the skill list is read from disk on every
   turn, so the next turn picks it up.

4. Confirm in a live turn: ask her to run the skill and check she uses
   `target: "host"` paths rather than claiming a tool she does not have.
